# 우리지금만나 설계 문서

작성일: 2026-09-23
상태: 백엔드, 데이터, 프론트엔드 구현 완료. 배포 준비 중 (`docs/deploy-design.md`)

## 0. 한 줄 요약

친구들이 각자 출발지를 입력하면, 가장 오래 걸리는 사람의 이동시간이 가장 짧은 "만남 거점"을 추천하고, 그 동네의 맛집, 카페, 놀거리, 행사를 함께 보여주는 웹 서비스.

## 1. 문제와 목표

- "중간에서 만나자"는 말은 쉽지만, 지도상 중간은 놀 게 없는 경우가 많다.
- 한 명만 1시간 타고 나머지는 10분인 약속은 불공평하다.
- 목표: 공평하면서도 놀 거리가 보장된 장소를 30초 안에 정하게 한다.

## 2. 확정된 결정 사항

| 항목 | 결정 | 이유 |
|---|---|---|
| 목적 | 실제 서비스 런칭 | 데이터 신선도, 공유 흐름, 비용까지 설계에 포함 |
| 추천 기준 | 공평함 (참여자 중 최대 이동시간 최소화) | 친구 사이에서 가장 납득되는 기준 |
| 지역 | 수도권 (서울, 경기, 인천) | 지하철망 촘촘, 공공 API 풍부 |
| 후보지 | 직접 큐레이션한 만남 거점 100곳 | "중간인데 놀 게 없다" 문제를 구조적으로 제거 |
| 입력 방식 | 방 만들고 링크 공유, 각자 출발지 입력 | 집 주소를 남에게 안 알려도 됨, 공유 자체가 바이럴 경로 |
| 로그인 | 없음, 익명 | 진입 장벽 제거 |
| 날짜 | 약속 날짜만 입력 (시간 없음) | 그 날 열리는 행사 필터링에 필요, 입력 부담 최소 |
| 이동시간 계산 | 지하철 그래프 직접 구축, 전 역 최단시간 사전 계산 | 비용 0, 응답 즉시, 외부 API 장애 무관 |
| 콘텐츠 | 맛집과 카페, 놀거리, 행사와 전시, 동네 분위기 한 줄 | 전부 무료 API 또는 수동 큐레이션 |
| 기술 스택 | FastAPI(Python) + Next.js + Supabase Postgres | 핵심 로직은 Python, 프론트는 얇게, 배포는 git push |
| 운영 비용 | 거의 0원 | 무료 티어와 공공데이터만 사용 |
| 만남 지역 | 방 만들 때 서울, 경기, 인천 복수 선택(화면에서는 처음에 아무것도 고르지 않은 상태, 1개 이상 골라야 만들 수 있음). 추천 화면 필터는 보는 사람 화면에서만 바뀜 | 멀리 가기 싫은 모임이 지역을 제한할 수 있게 |
| 테마 | 맛집, 카페, 술자리, 놀거리 중 하나(선택). 가장 공평한 곳보다 5분 이내로 더 걸리는 거점 중 테마에 맞는 곳을 앞에 둠 | 공평함은 5분까지만 양보하고 모임 성격을 반영 |
| 참가자 빼기 | 링크를 가진 누구나 빼고 다시 넣을 수 있음. 삭제가 아니라 계산 제외 | 못 오는 사람이 생겨도 방을 새로 만들지 않게. 되돌릴 수 있어야 실수에 안전 |

## 3. 사용자 흐름

1. **방 만들기**: 모임 이름, 약속 날짜, 만남 지역(서울, 경기, 인천 복수), 테마(선택)를 입력. 짧은 코드 링크 생성 (예: `/r/k3x9pq`).
2. **참여**: 링크를 열면 닉네임과 출발지 입력. 출발지는 지하철역 선택 또는 주소 검색. 한 브라우저에서 여러 명을 대신 넣을 수 있고, 못 오는 사람은 누구나 빼거나 다시 넣을 수 있다. 로그인 없음.
3. **추천**: 참여자 2명 이상이면 추천 5곳 표시 (1단계는 10초 폴링). 지역과 테마는 각자 화면에서 바꿔볼 수 있다. 카드에 사람별 소요시간과 공평도.
4. **둘러보기**: 거점을 고르면 그 동네의 맛집, 카페, 놀거리, 행사.
5. **만료**: 약속 날짜 7일 뒤 방과 참여자 데이터 자동 삭제.

### 프라이버시 원칙

- 원문 주소는 저장하지 않는다.
- 좌표는 소수점 3자리(약 100m)로 반올림해서 저장한다.
- 화면에는 "가까운 역" 이름만 보여준다. 다른 참여자에게 좌표는 노출하지 않는다.

## 4. 아키텍처

```
[Next.js (Vercel)]  --HTTP-->  [FastAPI (Render)]  --SQL-->  [Supabase Postgres]
                                     |
                                     +--> 카카오 로컬 API (맛집, 카페, 놀거리, 지오코딩)
                                     +--> 서울시 문화행사 API, KOPIS (행사)

[오프라인 스크립트 (Python)]  --> 공공데이터로 지하철 그래프 생성
                              --> 전 역 최단시간 계산 --> station_times 테이블 적재
```

|---|---|---|

| frontend | 화면 4개 (만들기, 참여, 추천, 둘러보기) + 카카오맵 | Vercel |

| scripts | 지하철 그래프 생성과 최단시간 계산. 노선 변경 시에만 재실행 | 로컬 실행 |

## 5. 데이터 모델

| 테이블 | 핵심 컬럼 | 비고 |
|---|---|---|
| rooms | id, slug, title, meet_date, regions, theme, created_at, expires_at | expires_at = meet_date + 7일. regions는 서울, 경기, 인천 중 1개 이상. theme은 없을 수 있음 |
| participants | id, room_id, nickname, lat, lng, nearest_stations, active, created_at | lat/lng 반올림. nearest_stations는 역 id와 도보분 최대 3개 (JSON). active가 거짓이면 계산에서 제외 |
| stations | id, name, line, lat, lng | 수도권 전체 791개 (노선별 노드, 물리적 역 그룹은 646개) |
| hubs | station_id, name, lat, lng, region, tags, themes, vibe_summary | 큐레이션 100곳. region은 서울/경기/인천. themes는 food, cafe, drink, play |
| station_times | from_station_id, to_station_id, minutes | 오프라인 사전 계산, 124,978행 (노드 791개 x 거점 노드 158개) |
| content_cache | hub_id, kind, cache_key, payload, fetched_at | kind는 food, cafe, play, event. event는 cache_key에 날짜 포함 |

## 6. 추천 알고리즘

1. 후보: 방(또는 요청)의 지역에 속한 거점만. 계산에는 빠지지 않은 참여자만 쓴다.
2. 참여자 p의 거점 h까지 소요시간:
   `time(p, h) = min over s in p.nearest_stations ( walk(p, s) + station_times[s][h] ) + 5분(거점역 하차 후 도보)`
3. 거점 점수: `score(h) = max over p ( time(p, h) )`. 작을수록 좋음.
4. 동점이면 `sum over p ( time(p, h) )`가 작은 쪽 우선.
5. 테마가 있으면, 가장 작은 점수보다 5분 이내로 큰 거점 중 테마에 맞는 곳을 앞에 둔다. 그 뒤는 3, 4번 순서 그대로. 5분은 측정값이 아니라 고른 값이다 (`backend/data/SOURCES.md`).
6. 상위 5곳 반환.
7. 화면 표시: "가장 오래 걸리는 사람 약 32분, 차이 9분" 형태로 공평도 함께 표시. 펼친 카드마다 최대 시간이 가장 빠른 거점보다 크면 "가장 빠른 곳보다 N분 더"를 붙인다. 테마 때문에 앞에 온 거점뿐 아니라 그 차이가 있는 모든 카드가 해당한다.

### 역간 시간표 생성 규칙 (오프라인)

- 노드: 역. 같은 역 이름의 다른 노선은 별도 노드로 두고 환승 간선으로 연결.
- 간선 가중치: 공공데이터의 역간 소요시간. 없으면 기본 2분.
- 환승 간선: 기본 5분. 환승 소요시간 데이터가 있으면 그 값 사용.
- 각 노드에서 다익스트라를 돌려 전 쌍 최단시간 산출.
- 도보시간: 직선거리 x 1.3 / 시속 4km.

## 7. 콘텐츠 출처 (전부 무료)

| 종류 | 출처 | 조건 |
|---|---|---|
| 맛집, 카페 | 카카오 로컬 카테고리 검색 (FD6, CE7) | 거점 반경 600m, 일 30만 회 무료 |
| 놀거리 | 카카오 로컬 키워드 검색 | 키워드: 방탈출, 보드게임카페, 노래방, 볼링장, 만화카페 |
| 행사, 전시 | 서울시 문화행사 정보 API, KOPIS 공연예술통합전산망 | 약속 날짜에 열리는 것, 거점에서 1.5km 이내 |
| 분위기 한 줄 | hubs.vibe_summary에 직접 작성 | 초안 100곳 작성 후 함께 다듬기 |

- 맛집, 카페, 놀거리는 거점별, 종류별로 24시간 캐시. 맛집과 카페는 정렬별로 따로 캐시한다.
- 맛집과 카페는 정렬을 고를 수 있다: 추천순(기본)과 가까운 순. 추천순은 카카오의 정확도순이다. 별점이나 리뷰 수가 아니라 카카오가 매긴 순서라서 화면에서도 인기순이라고 부르지 않는다. 가까운 순을 기본으로 두지 않는 이유: 큰 역은 반경 600m 안에 음식점이 1,000곳쯤 있어서 가까운 15곳이 역 안의 매점과 프랜차이즈로 채워진다(2026-10-06 강남, 홍대입구, 판교에서 확인). 별점순과 리뷰순은 그 데이터를 주는 공식 API가 없어 만들지 않는다.
- 카페는 분류 이름이 `음식점 > 카페`로 시작하는 곳만 보여준다. 카카오의 카페 분류(CE7)에 만화카페, 보드카페, 키즈카페, 모임 공간이 섞여 있기 때문이다. 세부 종류가 없는 `테마카페`도 뺀다(방탈출, 공방 같은 체험 공간이 대부분). 걸러내고도 15곳을 채우려고 3쪽까지 읽는다.
- 놀거리는 검색어 여러 개를 합친 목록이라 늘 가까운 순이다.
- 행사는 거점별, 날짜별로 24시간 캐시.
- 경기와 인천 거점의 행사는 1단계에서 KOPIS만 적용. 서울시 API는 서울 거점만.
- KOPIS 공연 목록에는 공연장 좌표도 공연장 id도 없다. 공연 상세에서 공연장 id를, 공연장 정보에서 좌표를 얻는다(공연장마다 호출 두 번). 좌표는 지역과 공연장 이름을 키로 30일 캐시한다. 요청 중에는 새 공연장을 6곳까지만 찾고(`MAX_NEW_VENUE_LOOKUPS`), 나머지는 매일 도는 `scripts.warm_kopis_venues`가 앞으로 14일치를 미리 채운다. 그래서 캐시가 채워지기 전의 첫 요청은 일부 공연만 보일 수 있다. 한 공연장의 조회가 실패하면 그 공연장만 건너뛰고(캐시하지 않는다), 세 번 연달아 실패하면 KOPIS가 막고 있다고 보고 그 요청에서는 더 찾지 않는다. 좌표가 없다고 나온 공연장은 하루 뒤에 다시 찾는다.

## 8. 에러 처리

| 상황 | 처리 |
|---|---|
| 주소를 좌표로 못 바꿈 | 역 직접 선택으로 안내 |
| 좌표가 수도권 밖 | "아직 수도권만 지원해요" 안내, 저장하지 않음 |
| 참여자 20명 초과 | "참여 인원이 가득 찼어요 (최대 20명)" 안내, 저장하지 않음. 계산에서 뺀 사람도 20명에 포함 |
| 가까운 역이 2km 초과 | 도보 대신 "버스 15분" 고정값 적용, 결과 카드에 표시 |
| 카카오 또는 행사 API 실패 | 캐시된 값 사용. 없으면 그 탭만 "지금 불러올 수 없어요". 추천 자체는 항상 표시 |
| 참여자 1명 | 결과 대신 "친구를 초대하세요" 대기 화면 |
| 만료된 방 링크 | "약속이 지난 방이에요" 안내 페이지 |
| 없는 역 id로 참여 요청 | "역을 찾을 수 없어요" |
| 그 방의 참가자가 아닌 id로 빼기 요청 | "참여자를 찾을 수 없어요" |
| 주소 검색 실패 | 빈 목록과 "지금 불러올 수 없어요". 역 선택은 계속 가능 |
| 고른 지역에 추천할 거점이 없음 | "이 지역엔 추천할 곳이 없어요. 지역을 넓혀보세요." (프론트 문구) |
| 전체 지역인데 추천이 비어 있음 | "경로를 계산하지 못했어요. 방을 새로 만들어 다시 시도해주세요." (프론트 문구) |
| 열어둔 거점이 추천에서 사라짐 | "추천이 바뀌었어요" 안내 후 추천 화면으로 (프론트 문구) |
| 주변 장소 0건 | "근처에서 찾지 못했어요" (프론트 문구) |
| 입력 검증 실패 (422 목록 응답) | "입력을 다시 확인해주세요" (프론트 문구) |
| 서버에 닿지 못함 | "연결이 불안정해요. 잠시 후 다시 시도해주세요." (프론트 문구) |
| 같은 곳에서 짧은 시간에 너무 많이 요청함 (429) | "요청이 너무 많아요. 잠시 후 다시 시도해주세요." (백엔드 `app/ratelimit.py`의 `MSG_TOO_MANY_REQUESTS`) |
| 첫 응답이 4초 넘게 걸림 (무료 서버가 잠들었다 깨는 중) | "서버를 깨우는 중이에요. 최대 1분쯤 걸려요." (프론트 문구, `MSG_WAKING`) |
| 추천 카드에 이동시간 구간이 없음 | "이동시간을 불러오지 못했어요" (프론트 문구, `MSG_LEGS_MISSING`) |
| 방 만들기에서 모임 이름이 비어 있음 | "모임 이름을 적어주세요" (프론트 문구, `MSG_TITLE_REQUIRED`) |
| 방 만들기에서 날짜가 없거나 오늘 이전 | "오늘 이후 날짜를 골라주세요" (프론트 `MSG_DATE_REQUIRED`, 백엔드 `MSG_DATE_PAST`. 서버는 한국 시간 기준으로 본다) |
| 방 만들기에서 날짜가 1년(365일)보다 뒤 | "약속 날짜는 1년 안으로 골라주세요" (프론트와 백엔드 `MSG_DATE_TOO_FAR`) |
| 방 만들기에서 지역을 하나도 고르지 않음 | "만날 지역을 하나 이상 골라주세요" (프론트 문구, `MSG_REGION_REQUIRED`) |
| 출발지 등록에서 닉네임이 비어 있음 | "닉네임을 적어주세요" (프론트 문구, `MSG_NICKNAME_REQUIRED`) |
| 출발지 등록에서 출발지를 고르지 않음 | "출발지를 골라주세요" (프론트 문구, `MSG_ORIGIN_REQUIRED`) |
| 역 또는 주소 검색 결과 0건 | "찾지 못했어요. 다른 이름으로 검색해보세요." (프론트 문구, `MSG_NO_SEARCH_RESULT`) |
| 링크 복사 실패 | "복사하지 못했어요. 주소창의 링크를 직접 복사해주세요." (프론트 문구, `MSG_LINK_COPY_FAILED`) |

## 9. 테스트 전략

- pytest 단위 테스트
  - transit: 그래프 최단시간, 환승 페널티 반영, 도보시간 계산
  - ranking: 한 명만 멀리 가는 케이스에서 공평한 거점이 이기는지, 동점 처리
  - geocoding: 카카오 응답 파싱 (고정 응답 파일 사용), 수도권 밖 판정
  - places, events: 응답 파싱과 캐시 히트/미스
- API 통합 테스트: FastAPI TestClient로 방 생성부터 결과 조회까지 전체 흐름
- 외부 API는 전부 모킹. 실제 호출은 배포 전 수동 스모크 테스트
- 프론트: 결과 페이지 렌더링 최소 테스트

## 10. 단계 구분

### 1단계 (첫 런칭)

- 방 생성, 참여, 결과 화면

- 거점 투표 기능
- 카카오톡 공유 카드
- 경기, 인천 행사 데이터 보강
