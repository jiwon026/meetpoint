# 프론트엔드 설계 문서

작성일: 2026-10-02
상태: 설계 확정 (2026-10-02). 구현 계획은 `dev/active/frontend/frontend-plan.md`
관련 문서: `docs/design.md`(제품 설계), `dev/active/transit-data/transit-data-context.md`("다음 계획에 넘길 것")

## 0. 한 줄 요약

화면 4개(방 만들기, 참여, 거점 추천, 거점 주변)짜리 Next.js 프론트를 새로 만들고, 그 화면이 필요로 하는 백엔드 보강(지역 선택, 테마, 주소 검색, 노선 목록)을 함께 넣는다. 로컬에서 끝까지 도는 것이 완료 기준이다.

## 1. 범위

### 이번에 하는 것

- `frontend/` 신규 (Next.js App Router, TypeScript, Tailwind CSS)
- 백엔드 보강 다섯 가지: 지역 선택, 테마, 주소 검색 프록시, 거점 노선 목록, 참가자 빼기
- `docs/design.md` 갱신 (2, 3, 5, 6, 8절)
- 로컬 E2E 흐름 테스트 1개

### 이번에 하지 않는 것

| 항목 | 이유 |
|---|---|
| 배포 (Vercel, Railway, Supabase) | 다음 계획으로 분리. DB 이전, 키 등록, 도메인이 한 묶음 |
| 투표, 1차 장소 확정, 약속 카드 | `design.md` 2단계 기능. 참가자 신원과 새 테이블 필요 |
| 카카오톡 공유 카드 | 2단계. 이번엔 링크 복사와 기기 기본 공유창으로 대체 |
| 세부 권역 (강남, 서초권 등) | 거점 데이터에 서울, 경기, 인천 구분만 있음 |
| 이동 수단 선호, 정렬 옵션, 공평도 점수 | 시간 모델과 순위 규칙에 해당 개념 없음 |
| 참가자 출발지 수정, 완전 삭제 | 익명이라 본인 확인 수단(토큰)이 먼저 필요. 대신 "빼기, 다시 넣기"를 둔다 (3.6) |
| 모임 시간 | 날짜만 받기로 확정 (`design.md` 2절) |
| 장소 별점, 리뷰 수, 사진, 해시태그, 출구 안내 | 카카오 로컬 API가 주지 않는 데이터. 지어내지 않는다 |
| 방장, 로그인, 알림 | 익명 서비스 |

## 2. 확정된 결정

| 항목 | 결정 | 이유 |
|---|---|---|
| 화면 구성 | 4단계 화면, 단계 표시줄. 하단 탭 없음 | 2~4단계는 방이 있어야 열려서 탭으로 두면 죽은 탭이 생김 |
| 지역 선택 | 방 만들 때 서울, 경기, 인천 복수 선택(기본 전부). 방에 저장 | `transit-data-context.md` 2026-09-28 결정 |
| 지역 필터 | 추천 화면의 필터는 보는 사람 화면에서만 바뀜 (URL 쿼리) | 방 수정 API와 동시 수정 충돌을 피함 |
| 테마 | 맛집, 카페, 술자리, 놀거리 중 하나(선택). 방에 저장, 추천 화면에서 바꿔보기 가능 | 근거 데이터가 있는 네 가지만. 스터디는 근거 없음 |
| 테마와 순위 | 가장 빠른 곳보다 5분 이내로 더 걸리는 거점 중 테마에 맞는 곳을 앞으로 | 공평함은 5분까지만 양보 |
| 주소 자동완성 | 백엔드 프록시 `POST /places/search` | 키가 브라우저에 안 나가고 pytest로 검증 가능 |
| 대리 입력 | 한 브라우저에서 여러 명 등록 허용 | 방장이 친구 출발역을 대신 넣는 경우 |
| 참가자 빼기 | 링크를 가진 누구나 빼고 다시 넣을 수 있음. 삭제가 아니라 계산 제외 | 못 오는 당사자는 링크를 다시 안 여는 경우가 많음. 되돌릴 수 있어야 실수와 장난에 안전 |
| 지도 | 카카오 지도. 추천 화면에 거점 5곳 핀, 주변 화면에 장소 핀 | 실제 위치 확인 |
| 색과 분위기 | 둥근 흰 카드와 넉넉한 여백 + 따뜻한 종이색 배경, 진녹색, 빨간 도장 포인트 | 시안 두 벌을 비교해 섞기로 결정 |
| 프론트 구조 | 브라우저가 FastAPI를 직접 호출. 서버 코드는 링크 미리보기 제목뿐 | "프론트는 얇게". CORS 설정은 이미 있음 |
| 타입 | 백엔드 OpenAPI에서 TS 타입 자동 생성 | Python 스키마가 원본 |
| 배포 | 이번 범위 밖 | 위 표 참고 |

## 3. 백엔드 변경

스키마가 바뀌므로 `dev.db`를 지우고 `init_db`, `pipeline.load` 순서로 다시 만든다 (마이그레이션 도구 없음, 기존 규약).

### 3.1 지역

- `Room.regions`: JSON 컬럼. 값은 `"서울"`, `"경기"`, `"인천"`. 1개 이상.
- `RoomCreate.regions`: 선택 입력. 생략하면 셋 다. 빈 목록이나 모르는 값은 422.
- `RoomOut.regions`: 응답에 포함.
- `GET /rooms/{slug}/result?region=서울&region=경기`: 쿼리가 없으면 방의 `regions`를 쓴다. 모르는 값은 422.
- 필터는 `rank_hubs` 호출 **전에** 후보 거점 목록에 적용한다. 상위 5곳을 자른 뒤 거르면 결과가 비어 보인다.

### 3.2 테마

- 테마 값: `food`(맛집), `cafe`(카페), `drink`(술자리), `play`(놀거리).
- `backend/data/manual/hubs.csv`에 `themes` 열 추가. 세미콜론으로 구분, 비어 있어도 됨.
- 초안 생성 규칙 (한 번 실행하는 스크립트로 채우고 눈으로 검토한 뒤, 이후에는 `hubs.csv`가 원본):

| 테마 | 조건 (하나라도 맞으면) |
|---|---|
| food | `hub_candidates.csv`의 `food` 수가 거점 100곳 중 상위 30위 이내, 또는 태그 `먹자골목`, `맛집`, `먹거리` |
| cafe | `cafe` 수 상위 30위 이내, 또는 태그 `카페거리` |
| play | `play` 수 상위 30위 이내, 또는 태그 `방탈출많음`, `영화관` |
| drink | 태그 `술집많음`, `밤늦게까지`, `포차` |

- `hub_candidates.csv`에 없는 거점은 태그로만 판정한다.
- 상위 30은 측정값이 아니라 고른 값이다. `SOURCES.md`에 근거와 함께 적는다.
- `pipeline.validate`는 `themes`에 모르는 값이 있으면 실패한다 (조용히 넘기지 않는다는 기존 원칙).
- `Hub.themes`: JSON 컬럼. `pipeline.load`가 적재.
- `Room.theme`: nullable 문자열. `RoomCreate.theme`은 선택 입력, `RoomOut.theme`으로 응답.
- `GET /rooms/{slug}/result?theme=cafe`: 쿼리가 없으면 방의 `theme`. `theme=any`는 테마 끔.

### 3.3 순위 규칙 (테마 반영)

`app/ranking/rank.py`에 상수 `THEME_TOLERANCE_MINUTES = 5`.

1. 지역으로 거른 후보마다 기존대로 점수를 낸다 (`max_minutes`, `sum_minutes`).
2. `best = 후보 중 가장 작은 max_minutes`.
3. 테마가 있고, 거점의 `themes`에 그 테마가 있고, `max_minutes <= best + 5`이면 "우선" 거점.
4. 정렬 키: `(우선이면 0 아니면 1, max_minutes, sum_minutes, hub_id)`. 상위 5곳.
5. 테마가 없으면 기존 순위와 완전히 같다.

5분은 측정값이 아니라 고른 값이다. `design.md` 6절과 `SOURCES.md`에 그렇게 적는다.

### 3.4 결과 응답 추가 필드

| 위치 | 필드 | 내용 |
|---|---|---|
| `RecommendationOut` | `lines: list[str]` | 거점 그룹에 속한 역 노드의 노선 이름, 중복 제거 후 정렬 |
| `RecommendationOut` | `theme_match: bool` | 적용된 테마가 거점 `themes`에 있으면 참 |
| `ResultOut` | `best_max_minutes: int \| None` | 3.3의 `best`. 추천이 없으면 `None` |
| `ResultOut` | `regions: list[str]` | 실제 적용된 지역 |
| `ResultOut` | `theme: str \| None` | 실제 적용된 테마 |

`best_max_minutes`가 필요한 이유: 테마에 맞는 곳이 5곳 이상이면 가장 빠른 거점이 5위 밖으로 밀린다. 그래도 카드에 "가장 빠른 곳보다 3분 더"를 정직하게 적을 수 있어야 한다.

### 3.5 주소 검색 프록시

- `POST /places/search`, 본문 `{"q": "..."}`: `q`는 공백을 뺀 뒤 2자 이상 30자 이하. 검색어가 집 주소일 수 있어 URL 쿼리에 넣지 않는다 (서버 접근 로그에 남지 않게).
- 카카오 키워드 검색을 REST 키로 호출해 수도권 범위 안의 결과 최대 5건을 `{items: [{name, address}], error: str | None}`로 돌려준다.
- 실패하면 `items`는 빈 목록, `error`는 "지금 불러올 수 없어요". 상태 코드는 200.
- 검색어는 저장하지 않고 로그에도 남기지 않는다.
- 외부 호출은 `places/kakao_local.py`의 `KakaoLocalClient`에 중심 좌표 없는 검색 메서드(`suggest`)를 더해 쓰고 `deps.py`에서 주입받는다.
- 프론트는 고른 항목의 `address`를 기존 `ParticipantCreate.address`로 제출한다. 좌표를 클라이언트에서 받는 새 경로는 만들지 않는다.

### 3.6 참가자 빼기, 다시 넣기

- `Participant.active`: bool 컬럼, 기본 참.
- `PATCH /rooms/{slug}/participants/{participant_id}`: 본문 `{active: bool}`, 응답 `ParticipantOut`. 그 방의 참가자가 아니면 404 "참여자를 찾을 수 없어요" (`MSG_PARTICIPANT_NOT_FOUND`, `design.md` 8절에도 추가).
- `ParticipantOut.active` 추가.
- `compute_result`는 `active`인 참가자만 쓴다. `active`가 2명 미만이면 `waiting`.
- 정원 20명은 빠진 사람을 포함한 전체 행 수로 센다 (빼기를 반복해 행이 무한히 늘지 않게).
- 빠진 사람의 데이터도 방 만료(약속일 7일 뒤) 때 함께 지워진다. 그 전에는 남아 있다.

## 4. 화면

모바일 우선. 넓은 화면에서는 가운데 최대 480px 열 하나.

### 공통

- 상단: 서비스 이름과 4칸 단계 표시줄 (1 방 만들기, 2 참여, 3 추천, 4 둘러보기). 지나온 단계는 눌러서 돌아갈 수 있다.
- 프로필 아이콘, 알림, 하단 탭 없음.
- 시간은 전부 "약 N분" (배차 대기 미포함).
- 화면 문구에 엠대시와 가운데 점을 쓰지 않는다.

### 4.1 방 만들기 `/`

- 입력: 모임 이름(1~40자), 약속 날짜(오늘 이후), 지역 칩 3개(기본 전부 켜짐, 최소 1개), 테마 4칸(맛집, 카페, 술자리, 놀거리. 다시 누르면 해제).
- 티켓 모양 카드 안에 폼을 넣는다.
- 안내 문구: "원래 주소는 저장하지 않아요. 약 100m 단위로 뭉갠 위치만 약속 7일 뒤까지 보관해요."
- 3단계 사용법 안내.
- 만들기 성공: `/r/{slug}`로 이동하고 링크를 클립보드에 복사, 토스트 표시.

### 4.2 참여 `/r/[slug]`

- 방 요약 카드: 모임 이름, 날짜, D-day, "약속 7일 뒤 자동 삭제", 지역과 테마.
- 공유: 링크 복사, 기기 기본 공유창(`navigator.share`가 있을 때만 버튼 표시).
- 출발지 등록 폼
  - 닉네임(1~20자)
  - 탭 두 개: "지하철역 선택"(기본), "주소, 건물명 검색"
  - 검색창 입력을 300ms 디바운스해서 역 탭은 `GET /stations?q=`, 주소 탭은 `POST /places/search` 호출
  - 역 결과는 이름과 노선 색 뱃지, 주소 결과는 이름과 주소
  - 고르면 확인 칩 표시, "출발지 등록" 버튼 활성
  - 등록 후 폼을 비워 다음 사람을 넣을 수 있게 한다 (대리 입력)
- 명부: "참여 N명", 사람마다 닉네임과 가까운 역 이름. 이 브라우저에서 넣은 사람은 "내가 등록" 표시. `via == "bus"`면 "버스 15분 포함".
  - 각 줄에 "빼기" 버튼. 누르면 "OO님을 계산에서 뺄까요? 다시 넣을 수 있어요" 확인 후 `PATCH ... {active: false}`.
  - 빠진 사람은 명부 아래 "빠진 사람" 묶음에 흐리게 표시하고 "다시 넣기" 버튼을 둔다.
  - 빠진 사람이 있으면 "참여 N명, 빠진 사람 M명"으로 표시한다.
- 하단 고정 영역: 참여(빠진 사람 제외) 2명 이상이면 "추천 보기 (N명)" 버튼, 1명 이하면 "친구를 초대하세요" 안내와 링크 복사.
- 이 브라우저에서 이미 누군가를 등록했으면 진입 시 `/r/{slug}/result`로 보낸다. 추천 화면의 "사람 추가"로 돌아올 때는 `?add=1`을 붙여 다시 보내지 않는다.
- 빠진 사람을 포함해 20명이면 폼 대신 "참여 인원이 가득 찼어요 (최대 20명)".
- 10초 폴링으로 명부 갱신. 빼기와 다시 넣기 직후에는 즉시 재조회.

### 4.3 거점 추천 `/r/[slug]/result`

- 지역 칩 3개와 테마 칩 4개. 누르면 URL 쿼리(`?region=...&theme=...`)가 바뀌고 즉시 재조회. 쿼리가 없으면 방의 기본값. 필터된 링크를 공유하면 받은 사람도 같은 필터로 본다.
- 카카오 지도: 거점 5곳 번호 핀. 펼친 카드의 핀을 강조.
- 1위 카드는 펼쳐진 상태로 시작. 다른 카드를 누르면 그 카드가 펼쳐지고 나머지는 접힌다.
- 접힌 카드: 순위, 거점 이름, 노선 뱃지, "서울, 최대 약 N분, 차이 N분"(지역 포함), 테마 도장.
- 펼친 카드: 위 내용에 더해 태그, 분위기 한 줄, 3칸 수치(최장, 평균, 차이), 사람별 막대, "이 동네 둘러보기" 버튼.
  - 평균은 `legs`에서 프론트가 계산한다.
  - 막대는 진녹색, 가장 오래 걸리는 사람만 빨강. 이 브라우저에서 넣은 사람 이름 옆에 "나".
  - `via == "bus"`면 "버스 15분 포함".
  - `theme_match`면 "테마에 맞아요" 도장. `max_minutes > best_max_minutes`면 "가장 빠른 곳보다 N분 더".
- 하단: "사람 추가"(4.2로), "결과 링크 복사".
- 10초 폴링.

상태별 표시:

| 상태 | 표시 |
|---|---|
| `waiting` (1명 이하) | "친구를 초대하세요"와 링크 복사, 사람 추가 버튼 |
| `ready`, 추천 0곳, 지역이 셋 다가 아님 | "이 지역엔 추천할 곳이 없어요. 지역을 넓혀보세요." |
| `ready`, 추천 0곳, 지역이 셋 다 | "경로를 계산하지 못했어요. 방을 새로 만들어 다시 시도해주세요." |
| 추천은 있는데 어떤 카드의 `legs`가 비어 있음 | 그 카드는 수치와 막대 대신 "이동시간을 불러오지 못했어요" |

### 4.4 거점 주변 `/r/[slug]/hubs/[hubId]`

- 헤더: 거점 이름, 노선 뱃지, 지역, 태그, 분위기 한 줄, "반경 600m".
- 거점 정보는 추천 결과 캐시에서 `hubId`로 찾는다. 캐시가 없으면 추천을 한 번 불러온다. 목록에 그 거점이 없거나 콘텐츠 API가 404면 "추천이 바뀌었어요" 토스트와 함께 4.3으로 보낸다. 거점 단건 조회 API는 만들지 않는다.
- 탭 4개: 맛집, 카페, 놀거리, 행사. "전체" 탭 없음. 방의 테마에 해당하는 탭부터 연다 (술자리는 맛집 탭, 테마 없으면 맛집 탭).
- 탭을 처음 열 때 `GET .../content?kind=`를 한 번 부른다. 폴링 없음. 행사 탭은 첫 로드가 느릴 수 있어 로딩 표시를 둔다.
- 카카오 지도: 거점 중심, 현재 탭의 장소 핀. 카드를 누르면 핀 강조.
- 장소 카드: 이름, 분류, "도보 약 N분"(`distance_m`을 분당 67m로 환산해 올림), 주소, "카카오맵에서 보기" 링크.
- 행사 카드: 포스터 이미지, 제목, 장소, 기간, 무료 여부, 링크.
- `error`가 오면 문구를 목록 위에 띄우고, `items`가 함께 오면 그대로 보여준다. 둘 다 비면 "지금 불러올 수 없어요"만.
- 결과가 0건이면 "근처에서 찾지 못했어요".

## 5. 디자인 방향

두 번째 시안의 배치(둥근 흰 카드, 넉넉한 여백, 하단 고정 버튼)에 첫 시안의 색을 입힌다.

| 토큰 | 값 | 쓰임 |
|---|---|---|
| 배경 | `#fcf9f5` | 페이지 |
| 카드 | `#ffffff`, 테두리 `#e5e2de`, 모서리 16px | 모든 카드 |
| 주색 | `#0f5238` (보조 `#2d6a4f`, 옅은 면 `#b1f0ce`) | 버튼, 선택된 칩, 막대 |
| 포인트 | `#b22a1d` | 도장, 가장 오래 걸리는 사람, 경고 |
| 글자 | `#1c1c1a`, 보조 `#404943`, 흐림 `#707973` | 본문 |

- 도장: 빨간 바탕에 흰 글자, 3도 기울임. "1위", "테마에 맞아요"에만 쓴다.
- 티켓 모양: 방 만들기 폼 카드와 참여 화면의 방 요약 카드에만 쓴다.
- 노선 뱃지: 실제 노선 색. 색 표는 `lib/lines.ts`에 두고, 표에 없는 노선은 회색.
- 글꼴: Pretendard 가변 글꼴 하나 (npm `pretendard`, `next/font/local`). 시안의 Domine, Work Sans, Plus Jakarta Sans는 한글이 없어 쓰지 않는다.
- 아이콘: `lucide-react`.
- 장식용 영어 문구와 이모지는 쓰지 않는다.

## 6. 프론트엔드 구조

```
frontend/
  app/
    layout.tsx                    글꼴, 공통 헤더, QueryClientProvider
    page.tsx                      4.1 방 만들기
    r/[slug]/
      layout.tsx                  링크 미리보기 제목(generateMetadata). 404와 410 안내는 RoomGate, ResultScreen, HubScreen이 각자 보여준다
      page.tsx                    4.2 참여
      result/page.tsx             4.3 추천
      hubs/[hubId]/page.tsx       4.4 주변
  components/
    room/      CreateRoomForm, RegionChips, ThemePicker
    join/      RoomGate, JoinScreen, JoinForm, OriginSearch, Roster, ShareButtons, RoomSummary
    result/    ResultScreen, FilterBar, HubCard, LegBars, FairnessStats
    hub/       HubScreen, HubHeader, ContentTabs, PlaceCard, EventCard
    map/       KakaoMap
    ui/        StepIndicator, Stamp, TicketCard, Toast, LineBadge, StickyAction
  lib/
    api/       client.ts, types.ts, schema.d.ts(생성물), hooks.ts
    constants.ts, regions.ts, themes.ts, lines.ts, format.ts, filter.ts, share.ts,
    messages.ts, myParticipants.ts, useDebounced.ts
```

- 화면 로직은 `*Screen.tsx` 컴포넌트에 두고 `app/` 페이지는 URL을 읽어 넘기기만 한다. 라우터 없이 컴포넌트를 테스트하기 위해서다.
- 스택: Next.js 16(App Router), TypeScript, Tailwind CSS 4, TanStack Query 5.
- 지도: `react-kakao-maps-sdk`. React 버전이 맞지 않으면 SDK 스크립트를 직접 로드하는 것으로 바꾼다. `KakaoMap` 컴포넌트 밖에서는 SDK를 건드리지 않는다.
- 환경 변수 (`frontend/.env.local`, 예시는 `.env.example`): `NEXT_PUBLIC_API_BASE`(기본 `http://localhost:8000`), `NEXT_PUBLIC_KAKAO_JS_KEY`. JS 키가 없거나 SDK 로드에 실패하면 지도 자리만 접히고 나머지는 동작한다.
- `.claude/launch.json`에 `frontend` 실행 설정 추가 (포트 3000).

### 데이터 흐름

| 화면 | 호출 | 갱신 |
|---|---|---|
| 4.1 | `POST /rooms` | 성공하면 4.2로 이동 |
| 4.2 | `GET /rooms/{slug}`, `GET /stations`, `POST /places/search`, `POST .../participants`, `PATCH .../participants/{id}` | 방 정보 10초 폴링, 등록과 빼기 직후 즉시 재조회 |
| 4.3 | `GET /rooms/{slug}/result` | 10초 폴링, 칩 변경 시 즉시 재조회 |
| 4.4 | `GET .../hubs/{id}/content` | 탭을 처음 열 때 한 번 |

- 폴링은 TanStack Query의 `refetchInterval`. 탭이 가려지면 멈춘다.
- `schema.d.ts`는 `npm run gen:api`로 백엔드 `/openapi.json`에서 생성한다 (`openapi-typescript`). 생성물은 커밋한다.

### 에러 처리

- `client.ts`가 실패 응답을 `ApiError(status, message)`로 바꿔 던진다.
  - `detail`이 문자열이면 그대로 `message` (백엔드 `MSG_*`가 화면 문구의 원본).
  - `detail`이 목록이면(FastAPI 검증 오류) "입력을 다시 확인해주세요".
  - 응답 자체가 없으면 "연결이 불안정해요. 잠시 후 다시 시도해주세요."
- 404는 "방을 찾을 수 없어요", 410은 "약속이 지난 방이에요" 안내 페이지와 "새 방 만들기" 버튼.
- 주소 등록이 422 또는 503이면 문구를 보여주고 역 탭으로 전환한다.
- 프론트에서만 쓰는 문구는 `lib/messages.ts`에 모으고 `design.md` 8절에도 적는다.

### 브라우저 저장

- `localStorage` 키 `wjm:room:{slug}:mine`에 이 브라우저에서 등록한 participant id 목록만 저장한다.
- `hub_id`, `station_id`는 저장하지 않는다 (데이터 재적재 시 바뀜).
- 펼친 카드와 선택한 탭은 메모리 상태로만 둔다.

## 9. 알려진 한계

- 역 id와 거점 id는 데이터를 재적재하면 바뀔 수 있다. 4.3의 `legs` 누락 처리와 4.4의 되돌려보내기가 그 대비책이고, 근본 해결(안정 id)은 이번 범위가 아니다.
- 참가자의 출발지는 고칠 수 없다. 잘못 넣었으면 그 사람을 빼고 새로 등록한다. 빠진 사람도 정원 20명에 들어간다.
- 빼기는 링크를 가진 누구나 할 수 있다. 되돌릴 수 있다는 것이 유일한 안전장치다.
- 지역 필터와 테마는 사람마다 다르게 볼 수 있어서, 같은 방을 보면서 서로 다른 1위를 이야기할 수 있다. 필터된 링크를 공유하면 같은 화면이 된다.
- 테마의 근거는 장소 개수와 수동 태그라서 정밀하지 않다. 상위 30과 5분은 고른 값이다.
