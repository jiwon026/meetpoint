# 테마 중복 선택 계획

지인 테스트 요청: 방을 만들 때 "어떤 모임인가요"를 여러 개 고를 수 있게 한다. 2026-10-08 홍보 전에 넣는다.

## 정한 것

- 여러 테마 중 **하나라도** 맞는 거점을 앞에 둔다(공평함은 여전히 5분까지만 양보). 모두 맞아야 하는 방식은 맞는 거점이 너무 적어 테마를 고른 효과가 안 보인다.
- 운영 DB는 기존 `rooms.theme` 열을 바꾸지 않고 `rooms.themes`(JSON, null 허용) 열을 **더한다**. 기존 방은 `themes`가 null이고 `theme` 값을 그대로 읽는다.
- 새 코드는 `theme`에도 첫 번째 테마를 계속 써 둔다. 새 코드를 되돌려도 방이 깨지지 않는다.
- 배포는 두 번으로 나눈다. Vercel이 Render보다 먼저 끝나므로 백엔드가 새 응답을 주기 전에 새 화면이 뜨면 안 된다.

## 순서

1. 백엔드 PR (기존 화면과 호환)
   - `rooms.themes` 열과 `migrations/002_room_themes.sql`
   - `POST /rooms`: `themes` 목록을 받는다. 예전 `theme` 하나도 계속 받는다.
   - `GET /rooms/{slug}`, 결과 응답: `themes` 목록을 더한다. 예전 `theme`(첫 번째 또는 null)도 계속 준다.
   - `GET /rooms/{slug}/result?theme=`: 여러 번 줄 수 있다. `any`가 있으면 테마 없음.
2. 운영 DB에 002 적용 (병합 **전에**. 새 코드는 `themes` 열을 읽으므로 열이 없으면 방 조회가 전부 실패한다)
3. 백엔드 PR 병합, 운영 확인
4. 프론트 PR
   - 방 만들기의 테마 선택을 여러 개로
   - 결과 화면의 테마 버튼을 여러 개로, 주소는 `?theme=food&theme=drink`
   - 참여 화면 요약, 둘러보기에서 먼저 여는 탭(고른 테마 중 정해진 순서의 첫 번째), 통계 값(쉼표로 이은 문자열)
5. 프론트 PR 병합, 운영 확인

## 나중에

- 응답과 요청의 예전 `theme` 하나짜리 필드 지우기. 기존 방이 모두 만료된 뒤(약속 날짜 + 7일)에 `rooms.theme` 열도 정리할 수 있다.
