# frontend 컨텍스트

Last Updated: 2026-10-02 (구현 완료, 최종 리뷰와 수정 반영 완료, 사용자 화면 확인 전. 브랜치 `feat/frontend`)

## 이 태스크가 뭔가

화면 4개(방 만들기, 참여, 거점 추천, 거점 주변)짜리 Next.js 프론트를 새로 만들고, 그 화면이 쓰는 백엔드 보강을 함께 넣는다. 설계 `docs/frontend-design.md`, 계획 `frontend-plan.md`(17개 태스크: 백엔드 1~7, 프론트 8~17). 배포는 이번 범위가 아니다.

## 상태

- 구현 완료: 계획의 Task 1~17 전부. 최종 리뷰는 2026-10-02에 끝났고 판정은 "수정 뒤 준비됨"이었다. 이 수정 묶음을 적용했다: 거점 주변 화면이 재조회 실패로 지워지지 않게 함, 방 만들기 성공 뒤 버튼을 잠금, 결과 화면에서 뒤로 가기가 참여 화면에 머물게 함(`?add=1`로 기록을 바꾼 뒤 이동), 흐름 테스트에 뒤로 가기, 참여 주소 리다이렉트, 비어 있지 않은 지역 필터 검사를 추가, 문서와 주석 정리. 사용자 화면 확인(스크린샷 4장, 카카오 키, 테마 목록 검토)은 남았다.
- 주소 탭 실제 확인(2026-10-02, 컨트롤러): 실제 카카오 API로 `POST /places/search`를 건물명(코엑스), 큰 건물 도로명 주소(테헤란로 152), 주거지 도로명 주소(신림로23길 16), 지번 주소(봉천동 1620-12), 아파트명(잠실엘스)에 불렀다. 제안 개수는 5, 5, 5, 1, 5였고, 매번 첫 제안의 주소로 등록하면 201이었다. 그래서 주소 탭은 장소 이름뿐 아니라 일반 주소에도 동작한다.

## 계획을 쓰면서 정한 것 (설계 문서에 반영함)

1. 주소 검색은 GET이 아니라 `POST /places/search`다. 검색어가 집 주소일 수 있어 URL에 넣으면 서버 접근 로그에 남는다.
2. 주소 검색은 기존 `keyword_search`(중심 좌표 필수)를 못 써서 `KakaoLocalClient.suggest`를 새로 둔다. 카카오 `rect` 파라미터로 수도권 범위만 찾는다.
3. 화면 로직을 `*Screen.tsx`로 빼고 페이지를 얇게 둔다. 컴포넌트 테스트에 `next/navigation` 모킹이 필요 없어진다.
4. 추천 카드의 지역은 뱃지가 아니라 요약 줄 맨 앞에 쓴다 ("서울, 최대 약 22분, 차이 10분"). 접힌 카드에서도 지역이 보이고 흐름 테스트가 이 줄로 지역 필터를 검증한다.
5. 필터 칩은 URL에 값이 있으면 응답의 적용 값보다 URL을 기준으로 켜고 끈다. 응답이 오기 전에 연달아 눌러도 어긋나지 않게 하기 위해서다.
6. `rank_hubs`는 시그니처를 그대로 두고 내부에서 `rank_with_preference`를 부른다 (기존 테스트 유지).
7. 타입 생성은 백엔드를 띄우지 않고 `app.openapi()`를 직접 뽑는다 (`frontend/scripts/gen-api.mjs`).

## 계획에서 벗어난 결정

- 화면 안내 문구(히어로, 단계 설명, 폼 라벨, 자리표시자, 제목)는 컴포넌트 안에 그대로 둔다. `lib/messages.ts`에는 상태, 오류, 안내 문구(`docs/design.md` 8절과 짝)만 모은다. 계획의 코드가 이미 그렇게 쓰였고 모든 라벨을 옮기면 간접 참조만 늘기 때문이다. 틀렸다면 나중에 문자열을 옮기면 된다.
- 사람이 확인해야 하는 단계는 실행을 막지 않는다. 테마 목록(Task 2 Step 10)은 초안으로 진행하고 최종 요약에 보여준다(`hubs.csv`를 고치고 세 명령으로 다시 적재). 화면 스크린샷은 Task 16 뒤에 컨트롤러가 한 번에 본다. 카카오 키(Task 15)는 없이 진행하고 지도 확인만 미룬다.
- 별도 git worktree 없이 메인 체크아웃의 `feat/frontend` 브랜치에서 진행했다 (앞선 두 계획과 같은 흐름, 사용자 선택).
- Task 2: `SOURCES.md` 계획 문구 "테마마다 거점의 약 3분의 1"은 실데이터와 맞지 않는다(food 51, cafe 36, drink 34, play 36). 규칙(상위 30곳 또는 태그)은 설계대로 두고 문장만 실제 개수로 고쳤다. 더 좁히고 싶으면 규칙을 조이고 `--force`로 테마를 다시 만든다.
- Task 7 실데이터 확인: "홍대입구, 수원, 잠실"의 1위는 어느 노선의 홍대입구 노드를 고르느냐에 따라 다르다. 2호선 노드면 판교 44분, 공항철도 노드면 서현 43분이 1위이고 판교가 2위다. 서울만 보면 어느 쪽이든 가락시장 54분이다. 코드 결함이 아니라 도보와 환승 분이 노드마다 다른 것이어서, 체크리스트 문구를 "2호선 홍대입구"로 고쳤다.
- Task 8: create-next-app이 만든 `frontend/AGENTS.md`와 `frontend/CLAUDE.md`는 그대로 둔다. `AGENTS.md`의 엠대시는 `next dev`가 그 블록을 다시 써서 고쳐도 남지 않는다. `package-lock.json`처럼 생성물로 보고 문장 부호 검사에서 `frontend/AGENTS.md`를 뺐다. 싫으면 두 파일을 지운다.
- Task 8: `@types/node`는 스캐폴드의 ^20이 아니라 ^24다. vitest 5의 peer 범위가 요구한다 (런타임은 Node 24).
- Task 8: Vitest 설정 파일은 Vite의 CJS 경고를 없애려고 `vitest.config.mts`로 했다.
- Task 12: `app/page.tsx`는 렌더 중에 `todayIso()`를 부르지 않고 `useSyncExternalStore`(서버 스냅샷은 빈 문자열)로 오늘 날짜를 읽는다. 사전 렌더된 HTML에 빌드 날짜가 박히고 하이드레이션 불일치가 나는 것을 막기 위해서다 (Task 9 리뷰에서 넘어온 판정).
- Task 13: 계획의 "확인을 취소하면 요청하지 않는다" 테스트는 아무것도 단언하지 않았다(MSW의 `onUnhandledRequest: "error"`는 fetch만 거부하고 테스트를 실패시키지 않는다). confirm이 불렸고 PATCH가 나가지 않았음을 단언하도록 고쳤다.
- Task 13: 설계 4.2는 두 명 미만일 때 고정 영역에 초대 안내와 링크 복사 동작을 함께 둔다고 했는데 계획의 코드는 안내만 있었다. 설계를 따라 복사 버튼을 추가했다. 그래서 이 상태의 참여 화면에는 "초대 링크 복사" 버튼이 두 개(위쪽, 고정 영역)이고, 테스트와 흐름 테스트는 이 이름을 범위 없이 찾지 않는다.
- Task 13: 출발지 검색 요청이 실패(네트워크, 5xx)해도 `OriginSearch`가 조용히 넘어가던 것을, 오류를 삼키지 않는다는 프로젝트 규칙에 따라 `error.message`를 보여주도록 고쳤다 (리뷰 Minor에서 1차 수정으로 승격).
- Task 17: 흐름 테스트의 프론트 서버를 `npm run dev`가 아니라 `npm run build && npm run start`로 띄운다. 이유와 알려진 범위는 "알려진 한계"의 개발 모드 404 항목. 실행이 1분 넘게 걸리고, 같은 `.next`를 쓰는 3000번 개발 서버는 꺼야 하며, 실행 뒤 `.next`에 e2e용 빌드(`NEXT_PUBLIC_API_BASE=http://localhost:8010`, 빈 카카오 키)가 남는다. 이어서 `npm run start`를 하려면 `npm run build`를 다시 한다.
- Task 17: `e2e/start-backend.mjs`는 `fs.rmSync` 대신 `existsSync`와 `unlinkSync`로 `e2e.db`를 지운다. Node 24 Windows에서 `rmSync`가 한글 경로를 만나면 프로세스가 오류 메시지 없이 비정상 종료(종료 코드 3221226505)한다.
- Task 17: `eslint.config.mjs`의 전역 무시 목록에 `coverage/**`, `playwright-report/**`, `test-results/**`를 더해 커버리지와 흐름 테스트 뒤에도 `npm run lint`가 깨끗하다.

## 리뷰에서 미룬 것 (최종 리뷰에서 추려 고칠 후보)

백엔드
- 서비스와 모델: `service.py`, `models.py`의 import 순서. `regions or room.regions`는 직접 호출자가 빈 목록을 주면 방 기본값으로 처리한다(HTTP 경로로는 불가능). 빈 값으로 지운 `themes`를 `fill_themes`가 다시 초안으로 채운다.
- 장소 검색과 로그: Kakao가 JSON이 아닌 200을 주면 500이 되고(`hub_content`도 같은 모양), `place_name`이 명시적 null이면 처리가 안 된다. httpx가 요청 URL 전체를 INFO로 로그에 남긴다(지오코더도 같다).
- 테스트 빈틈: 허용 오차 안의 선호 거점 사이 공정성 순서, 지역과 테마 조합, 빈 `documents`와 타임아웃, 만료된 방이나 bool이 아닌 본문의 PATCH, 테마별 최소 10곳 하한이 실제 개수보다 훨씬 낮음.
- 구조와 의미: `split_list`가 `pipeline/themes.py`에 있지만 `load.py`, `validate.py`도 쓴다(`pipeline/io.py`가 어울림). `theme_match`는 "테마가 붙은 거점"이라는 뜻이지 "테마로 앞에 올라온"이 아니다(독스트링이나 스키마 설명 필요).

문서
- `docs/design.md`: 9, 10절에 "결과 화면", "결과 페이지" 용어가 남음. (60~100곳, 약 700개, 약 49만 행 숫자와 8절 정원 행은 최종 리뷰 수정에서 고쳤다.)

프론트 공통
- 인프라: `frontend/.gitignore`의 중복 커버리지 줄, 기본 파비콘. `vitest.setup.ts`가 `localStorage`를 무조건 비움(node 환경 테스트에서 깨짐). `request()`가 빈 본문이나 JSON이 아닌 2xx에서 `SyntaxError`를 그대로 던짐. GET에도 `Content-Type`을 보내 CORS 사전 요청이 생김(백엔드가 허용). 폴링이 4xx 뒤에도 계속되고, 방이 만료돼도 이미 있는 데이터는 안내 없이 남음(`ResultScreen`, `RoomGate`). `keepPreviousData`가 슬러그를 바꾸면 다른 방 결과를 잠깐 보일 수 있음. 역 검색어를 백엔드 `max_length` 20으로 자르지 않음.

- 공통 UI: `Toast`는 같은 메시지를 연달아 보이면 타이머를 다시 시작하지 않고 마운트 시점에 이미 글자가 있어 스크린 리더가 못 읽을 수 있다. `LineBadge`는 긴 이름이 줄바꿈되고 숫자 뱃지의 전체 이름이 `title`에만 있다. `StepIndicator`의 `query`는 앞의 "?"를 포함해야 한다는 암묵적 약속이 있고 `ink-mute` 글씨와 `track` 배경 대비가 약 3.9:1이다. 테스트용 `next/link` 모킹이 모든 prop을 `<a>`에 펼친다.

## 알려진 한계

- 흐름 테스트는 `next dev`가 아니라 빌드한 서버(`next build` + `next start`)로 돈다. `next dev`(Next 16.3.8, Turbopack, Windows)에서는 흐름이 클라이언트 쪽 화면 이동 뒤 Next 자체의 404 화면에 닿는 일이 약 40% 확률로 있었다. 원인은 모른다. 앱 코드는 `notFound`를 부르지 않는다. 경로를 미리 한 번씩 열어 두는 방법은 효과가 없었다. 빌드한 서버에서는 연속 통과했고, 그래서 이 테스트는 개발 모드 동작을 덮지 않는다. 개발 모드 404는 앞으로 다음처럼 다룬다. 컨트롤러가 손으로 해 본 확인(클라이언트 이동 세 번, 404 없음)은 사라졌다는 증거가 아니다. 이동 한 번당 약 10%라면 세 번 연속으로 깨끗할 확률이 약 3분의 2(0.9의 세제곱)이기 때문이다. 배포 계획 전에 시간을 정해 두고 실험한다: (a) `next dev`에서 흐름을 10번 돌리면서 어느 응답이 404였는지(문서인지 `_rsc`인지, 어떤 경로인지) 기록, (b) 영문 경로의 저장소 복사본에서 같은 반복, (c) Turbopack을 끄고 같은 반복. 검증하지 않은 단서: 같은 기기에서 `fs.rmSync`가 프로젝트의 한글 경로에서 Node 24를 비정상 종료시켰으니, 한글 경로가 의심스러우면 가장 먼저 시험할 것(예: 영문 경로로 복사해 `next dev`로 같은 흐름을 반복).
- 역 id와 거점 id는 재적재하면 바뀔 수 있다. 추천 카드의 `legs` 누락 처리와 주변 화면의 되돌려보내기가 대비책이고 근본 해결(안정 id)은 범위 밖.
- 참가자 출발지는 고칠 수 없다. 빼고 새로 등록한다. 빠진 사람도 정원 20명에 들어간다.
- 빼기는 링크를 가진 누구나 할 수 있다. 되돌릴 수 있다는 것이 유일한 안전장치다.
- 지역과 테마 필터는 사람마다 다르게 볼 수 있다. 필터된 링크를 공유하면 같은 화면이 된다.
- 테마 판정(상위 30곳, 태그)과 허용 오차 5분은 고른 값이다.
- 장소 카드에 별점, 사진, 리뷰가 없다 (카카오 로컬 API가 주지 않는다).

## 최종 리뷰에서 나중으로 미룬 것

1. `RoomGate`와 `ResultScreen`은 방이 404나 410을 돌려주기 시작해도 묵은 내용을 보이고 폴링을 계속한다. 세 화면에 같은 규칙을 둔다(404와 410이면 화면을 안내로 바꾸고 폴링을 멈추고, 0이나 5xx면 데이터를 유지). 예를 들어 `lib/api/hooks.ts`에서 `refetchInterval`을 함수로 만든다.
2. 20번째 등록자는 "내가 등록"으로 기억되지 않는다. 뮤테이션의 훅 수준 `onSuccess`가 방 재조회를 기다리고, 방이 가득 차면 폼이 사라지며, `JoinForm`의 호출별 `onSuccess`는 언마운트된 옵저버에서는 불리지 않는다. `addMine`을 훅 수준으로 옮기거나 무효화를 기다리지 않게 한다.
3. "사람 추가"로 갔다가 돌아오면 지역과 테마 필터를 잃는다(두 이동 모두 쿼리를 싣지 않는다).
4. 거점 머리글은 "반경 600m"인데 행사는 1.5km 안에서 찾는다. `EventCard`는 `distance_m`를 보이지 않는다.
5. `PlaceCard`는 `url`이 비어 있어도 링크를 그린다.
6. 오류 카드가 네트워크 오류에도 "새 방 만들기"를 보인다. 404와 410에만 보이게 한다. `HubScreen`의 오류에는 만료된 방이어도 그 버튼이 없다.
7. 겹치는 UI 코드를 공용 조각으로 묶는다: 오류 카드(세 화면), `noSubscribe`와 `useSyncExternalStore`(두 곳), 링크 복사와 토스트(`useCopyInviteLink`와 `ResultScreen`), 번호 원 클래스(네 곳), 탭 목록 스타일(두 곳), 태그 칩(두 곳). 백엔드 테스트에서는 `NoGeocoder` 클래스와 `client` 픽스처(새 테스트 파일 세 개).
8. 필터 변경이 `router.replace`(서버 왕복)를 쓴다. `window.history.replaceState`면 즉시 바뀌고 칩을 빠르게 누를 때 낡은 필터가 끼는 경쟁도 없어진다.
9. 접근성 점검: 탭에 `tabpanel`과 `aria-controls` 없음, 메시지가 라이브 영역이 아님, 등록 뒤 포커스, 토스트 라이브 영역을 항상 마운트, 노선 뱃지 이름과 대비, 카드 머리 버튼의 `aria-controls`.
10. 메우면 좋은 테스트 빈틈: 참가자 변경이 방과 결과를 다시 불러오는지(지금은 흐름 테스트만 덮음), `useHubContent`, 백엔드의 지역과 테마 조합, 지도의 경계 효과.
11. `request()`가 빈 본문이나 JSON이 아닌 2xx를 `ApiError`로 감싸야 하고, `Content-Type`은 본문이 있을 때만 보내야 한다.
12. `split_list`는 `pipeline/io.py`로, `theme_match`에는 필드 설명을, 응답 스키마는 `Region`과 `Theme` 리터럴 타입을 써서 생성된 TypeScript에 유니온이 실리게 한다.
